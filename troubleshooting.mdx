Almost every failure state in Orbi Cloud is self-describing. Start at the [status page](https://orbi.build/api/): the **① Needs You** banner names the problem and gives you the fix button. This page explains what each failure means, what caused it, and exactly what to do to recover.

## Nothing Happens After I Label an Issue `ai-ready`

Work through this checklist before concluding something is broken:

<Steps>
  <Step title="Is it the connected repository?">
    Orbi only reads Issues in the one repository you have connected. If you labelled an Issue in any other repository — even one in the same organization — Orbi will not pick it up.
  </Step>
  <Step title="Has provisioning finished?">
    The Connected Repository card on the status page shows a **Provisioning Status**. Dispatch only begins once the status reads **Provisioned**. If it still shows provisioning, wait for it to complete.
  </Step>
  <Step title="Has 5 minutes passed?">
    Issue pickup runs on a timer, not an event webhook. Allow up to 5 minutes after applying the label before concluding nothing happened.
  </Step>
  <Step title="Did the label come back off?">
    If `ai-ready` was removed and a comment appeared on the Issue, a quota guard stripped it. You have either exhausted your free allowance or hit your monthly cap. Subscribe or wait for the next billing period, then re-apply the label.
  </Step>
  <Step title="Does the Issue already carry another `ai-*` label?">
    An Issue labelled `ai-in-progress` or `ai-merged` is not re-dispatched. Each Issue maps to one delivery. If you want to restart work, re-apply `ai-ready` only after the previous delivery has completed or been cleared.
  </Step>
</Steps>

## `ai-blocked`

An `ai-blocked` label is a deliberate stop, not a crash. Orbi determined that continuing automatically wasn't safe — a person needs to decide the next step.

**How to read it:** Open the Issue and read the comment Orbi left. It states the reason for the block.

**Common causes:**
- The repair loop exhausted its allowed rounds without producing a passing build
- The Issue requires an external precondition that isn't present in the repository
- The acceptance criteria ask for something the delivery environment cannot do

**How to recover:** Fix the underlying cause first, then re-apply `ai-ready` to restart.

<Warning>
  Removing `ai-blocked` alone does not restart anything — fix the cause first, then re-apply `ai-ready`.
</Warning>

### Acceptance Criteria the Environment Can't Satisfy

The delivery environment contains your repository and your test suite. It does not contain:

- Production credentials or deployment pipeline access
- Third-party service accounts
- A browser session against your live site
- Your other repositories

If your Issue asks Orbi to verify something that can only be confirmed in production — for example, "check that the payment webhook fires correctly in the live environment" — the delivery will block. Rewrite the criterion as something checkable from within the repository. Gather production evidence yourself and record it in the Issue or PR description.

## The Pull Request Looks Wrong

Comment on the Issue with the correction, or edit the Issue body directly. The next session picks up your update and restarts the delivery from the beginning. You do not need to close the Issue, cancel anything, or interact with the PR. If you decide you do not want the change at all, close the Issue.

## Provisioning Failed

The Connected Repository card shows the reason, the time of failure, a request ID, and the recommended next step.

| Reason | What to Do |
|---|---|
| GitHub App installation or authorization no longer valid | Reinstall or re-authorize the App in GitHub, then retry provisioning |
| Model credential was not accepted | Correct your key in model configuration; saving the corrected key retries automatically |
| Model service could not be reached | Check the base URL and key; saving retries automatically |
| Platform-side failure | Nothing — the platform recovers automatically; check back in 1–2 minutes |

<Note>
  Quote the request ID when you contact support. It lets the team locate your provisioning attempt immediately.
</Note>

## Can't Connect My Repository

| Message | Fix |
|---|---|
| Not authorized for the Orbi GitHub App | Add the repository to the App installation in GitHub Settings → Applications, then reload the connect page |
| Issues are disabled | Enable Issues in the repository's Settings → Features |
| A delivery is still in progress | Wait for `ai-merged` or `ai-blocked`, then rebind the repository |
| Repository list temporarily unavailable | Retry; use the **Enter manually** option if the problem persists |
| Repository format is invalid | Enter the repository as `owner/repository` |

## The GitHub App Was Uninstalled

The status page detects a missing App installation and offers a **Reinstall the Orbi GitHub App** button. Follow it to reinstall. Reinstalling on the same GitHub account or organization reconnects to your existing tenant — your delivery history and settings are intact. You may need to reconnect your repository afterwards if the binding was cleared.

## Issues Got Disabled

If Issues are turned off in your repository after you connected it, the status page detects the change and links to your repository settings. Re-enable Issues at **Settings → Features → Issues** in GitHub, then return to the status page.

## Quota Draining Faster Than Expected

Open the status page and check the **Monthly Cache Hit Rate** displayed on your usage card.

- Cache-miss tokens cost roughly **50× more** than cache-hit tokens.
- A cache hit rate below **90%** burns through your monthly token budget dramatically faster than expected.
- Large, vague Issues cost far more than small, specific ones — both in token usage and in repair rounds.

If your rate is low, write tighter, more specific Issues and break large tasks into smaller ones. See [Your First Issue](/first-issue) for guidance.

## Usage Shows `—`

A dash in the usage column means that work item never reported usage statistics back to the platform. It is a measurement gap, not a delivery failure — the delivery may have completed normally.

If measurement is unhealthy across the board (not just one item), the quota guard fails closed: it pauses new dispatch until measurement recovers, then clears itself automatically. No action is required from you.

## My Session Expired

Sign in again at [orbi.build/api/](https://orbi.build/api/). Nothing is lost. Your repository connection, model configuration, delivery history, and subscription all belong to your tenant, not to the browser session. Signing back in returns you to exactly where you were.

## Getting Help

The **Technical Support** card at the bottom of the status page links to the Telegram group, with a QR code for joining on a phone.

When you report a problem, include:

- What you did and what you expected to happen
- The Issue or PR URL
- The request ID (for provisioning failures — shown on the Connected Repository card)
- The exact wording of the status page banner or error message

<Warning>
  Never paste an API key, token, or credential into a support message, Issue, or pull request.
</Warning>
