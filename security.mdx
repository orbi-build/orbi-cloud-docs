Orbi Cloud's access is limited to the repositories you authorize in your GitHub App installation — no broader. Every grant is revocable by you directly from GitHub, without involving Orbi at all. This page states the boundaries plainly so you can make informed decisions about what you connect and when.

## What Orbi Can Access

Orbi reaches only what you explicitly hand it:

- **Your authorized repositories only.** Orbi acts within the repositories included in your GitHub App installation. It performs no discovery and has no access to repositories outside that installation — including other repositories in the same organization or account.
- **Your identity via OAuth.** The sign-in flow requests the `user:email` scope only. This establishes who you are so Orbi can associate your session with your tenant. It does not grant any repository access.
- **Minimum repository permissions.** The GitHub App requests only the permissions required to carry out the full delivery lifecycle. The seven permissions are: **Issues** (read and write — labels, comments, milestones), **Pull requests** (read and write — open, review, and merge the delivery PR), **Contents** (read and write — fetch the repository and push the delivery branch), **Checks** (read-only — read CI results at each gate), **Workflows** (read and write — push files under `.github/workflows/` without silent rejection), **Variables** (read and write — synchronize delivery state), and **Administration** (read and write — register a deploy key during initial provisioning only). A full explanation of each permission appears in [Install the GitHub App](/install-app).

## Revoking Access

You can cut off Orbi's repository access at any time directly from GitHub:

1. Go to **GitHub Settings → Applications → Installed GitHub Apps**.
2. Find **Orbi** and select **Configure**.
3. Scroll to the bottom and select **Uninstall**.

Access ends immediately when the uninstall completes. This control lives entirely on GitHub — you do not need Orbi's cooperation, a support request, or any action inside the Orbi interface to revoke access.

<Note>
  Revoking App access and cancelling your subscription are separate actions. Uninstalling the App stops Orbi from reading your repository but does not cancel your billing. Cancel your subscription from the status page if you want to stop both.
</Note>

## API Key Storage

If you configure a bring-your-own-key (BYOK) model credential, Orbi handles it as follows:

- The key is **encrypted at rest with AES-256-GCM**.
- It is shown back to you **masked only** (for example, `••••1234`) — never in full after the initial save.
- It is **never written to logs** and never included in support evidence bundles.
- It is **never shown in any shareable interface** — not on the status page, not in delivery details, not anywhere a second party could read it.

<Warning>
  Do not email your key or paste it into an Issue, PR, or comment. Keys in Issue bodies stay in edit history and may be visible to anyone who can read your repository.
</Warning>

## Tenant Isolation

Every customer's delivery environment runs in strict isolation:

- Each tenant's delivery environment is a **separate OS user** with its own home directory and credentials.
- Environments **cannot read each other's files** — the filesystem boundary is enforced at the OS level.
- Every database read is **scoped to the requesting tenant** — no query can return another tenant's records.
- Cross-tenant access and credential leakage are treated as **release blockers**, not ordinary bugs. A build that could allow one tenant to reach another's data does not ship.

## What the Delivery Environment Cannot Access

The delivery environment contains your repository and test suite, and nothing else. The following are explicitly outside its reach:

- Your production credentials or deployment pipeline
- Your third-party service accounts
- A browser session against your live site
- Your other repositories

<Note>
  This is both a security property and a practical constraint. If your acceptance criteria require production evidence, the delivery will block. See [Your First Issue](/first-issue) for how to write Issues that work within this boundary.
</Note>

## What Orbi Writes to Your Repository

Orbi's write surface is narrow and fully traceable:

- It **pushes commits to the branch it creates** for a delivery.
- It **merges the reviewed pull request** into your base branch once the review verdict is clean and the merge gate passes.
- It does **not push directly to your base branch** outside that reviewed merge flow.
- It **never force-pushes a shared branch** and never moves or deletes an existing tag.
- The complete record of every commit, label change, and comment Orbi made stays in your repository — nothing is hidden or off-ledger.

## Branch Protection

If your base branch requires approving reviews before merge, every delivery will stop at the merge step. Orbi opens and merges as the same GitHub App identity, and GitHub forbids an actor from approving its own pull request — so the merge is blocked.

The connect-repository page warns about this and explains three ways to resolve it. Requiring human approval on every delivery is a legitimate policy choice — just be deliberate about making it. See [Connect a Repository](/connect-repository#branch-protection) for the resolution options.

## Your CI and What Orbi Guarantees

Orbi's merge gate and release gate both read your repository's check runs. The guarantee Orbi can offer is only as strong as your test suite:

- **Good tests → strong guarantees.** If your CI catches regressions reliably, the merge gate is a meaningful quality signal.
- **No CI → gates pass on review judgement alone.** When there are no check runs, the gate records "no check runs" as evidence and relies entirely on the independent review session's verdict.

Running no CI is permitted and recorded honestly in the delivery evidence. It is your call — Orbi does not require CI, but it cannot manufacture confidence that your tests don't provide.

## Platform Upgrades

Platform upgrades never interrupt a delivery that is already executing. A deployment may update the code that handles new work, but it cannot restart or cancel a session that is mid-flight. The same guarantee applies to quota guards: they act only on newly dispatched Issues and cannot stop a delivery that has already started.

## Reporting a Security Problem

Use the Telegram group linked from the **Technical Support** card on the [status page](https://orbi.build/api/). Describe the issue clearly without including credentials, tokens, keys, or other sensitive values in the message. For suspected vulnerabilities, the Telegram group reaches the team directly.
