When you connect a repository, Orbi immediately begins provisioning a dedicated environment for it. The process takes one to two minutes and runs entirely in the background — there is nothing for you to do and no way to speed it up. The status page at orbi.build/api/ refreshes itself while provisioning runs, so you can watch progress without reloading.

## What Happens During Provisioning

Orbi builds an isolated environment that belongs exclusively to your repository and your account. No other tenant shares it. Each environment is isolated at the OS level.

Inside that environment, Orbi:

1. Clones your repository.
2. Installs the delivery engine.
3. Runs the engine's setup step.

The setup step is declarative. It inspects your repository's labels and creates any `ai-*` labels that are missing — `ai-ready`, `ai-in-progress`, `ai-pr-opened`, `ai-fix-needed`, `ai-merged`, and `ai-blocked`. If a label exists but has drifted from the expected colour or description, setup corrects it. Setup never deletes labels. Your own labels — `bug`, `enhancement`, and anything else you have created — are never touched.

## Watching Provisioning

Open the Connected Repository card on the status page at orbi.build/api/. The **Provisioning Status** column tells you exactly where things stand.

| Status | Meaning |
|---|---|
| **Provisioning** | Running — usually finishes in 1–2 minutes; the page refreshes itself |
| **Provisioned** | Complete — file your first Issue when you are ready |
| **Provisioning failed** | Stopped — the card names the reason and the next step |
| — | Not yet triggered — no repository is connected |

## When Provisioning Fails

When provisioning stops, the card always names a specific reason and tells you the next step. The four failure classes below cover every case you are likely to encounter.

### GitHub App Not Valid

**Cause:** The Orbi GitHub App was uninstalled after you connected your repository, or access to the specific repository was removed.

**Fix:** Reinstall the App or re-authorize it for your repository, then retry. The card links directly to the connect page so you do not have to navigate there manually.

### Model Credential Rejected

**Cause:** Your BYOK API key was rejected by the model provider — typically because the key is invalid, has been revoked, or belongs to a different account.

**Fix:** Open model configuration and correct the key. Saving the corrected key retries provisioning automatically — you do not need to do anything else.

### Model Service Unreachable

**Cause:** The provider's base URL appears wrong, the key does not match the configured endpoint, or the provider itself is experiencing an outage.

**Fix:** Open model configuration and verify both the base URL and the key. Saving retries provisioning automatically. If the provider is down, wait for it to recover and then save the configuration again to trigger a retry.

### Platform-Side Failure

**Cause:** Something went wrong inside Orbi's infrastructure — nothing attributable to your GitHub App installation or model configuration.

**Fix:** No action is required. Orbi recovers platform-side failures automatically. Check the status page again in a minute or two. If the failure persists, contact support via the Telegram group linked from the status page and include the **request ID** shown on the card — it lets the team locate your run immediately.

## Automatic Retries

Provisioning retries automatically a limited number of times after a failure. The card tells you whether retries are still ongoing or have been exhausted.

Fixing a tenant-side cause re-arms the retry counter. If provisioning failed because of a bad model key, saving a corrected key in model configuration triggers a fresh attempt even after retries are otherwise exhausted.

For platform-side failures, you do not need to take any action — recovery and retries happen automatically.

<Note>
  Saving a corrected model configuration always retries provisioning, regardless of whether the retry counter is exhausted. You never need to disconnect and reconnect a repository just to retry.
</Note>

## After Provisioning Succeeds

Once the status shows **Provisioned**, your environment is ready and nothing further is required before you start delivering work. The environment stays provisioned between deliveries — Orbi does not tear it down and rebuild it for each Issue.

If you connect a different repository later, Orbi provisions a fresh, separate environment for it. The environment for your original repository is unaffected.
