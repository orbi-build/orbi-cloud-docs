连接仓库是告诉 Orbi 它可以处理哪个仓库的 Issue，以及往哪个分支提交拉取请求。

连接是自助的：你在连接页上挑好仓库和基础分支，开通随即开始。同一时间能连几个仓库取决于你的套餐：Free 和 Solo 是一个，Pro 最多五个。换仓库一律要先停用旧的。详见[限制与配额](/zh/limits-and-quotas)。

## 连接

在状态页上点 **连接仓库**；已经连过仓库的话，点 **管理仓库**，打开的是同一个页面。

<Frame caption="连接仓库页，显示仓库和基础分支两个列表">
  <img src="/images/zh/connect.png" alt="连接仓库页，显示仓库和基础分支两个列表" />
</Frame>

1. **仓库**：从你的 GitHub App 安装所覆盖的仓库里挑。列表很长时，在搜索框里输入名字的一部分就能筛选。
2. **基础分支**：Orbi 提交拉取请求的目标分支。选中一个仓库之后，页面会载入它真实的分支列表并预选默认分支，所以通常你只需要确认。
3. 点 **连接仓库**。处理期间按钮会变成 **正在连接…**，不用再点一次。

接着页面会显示 **仓库已连接**，并开始[开通](/zh/provisioning)。页面会自己更新，环境准备好之后会出现一个 **创建第一个 Issue** 按钮。

<Note>
如果仓库是空的，一个 commit 都没有，页面会提示你。连接时 Orbi 会在基础分支上提交一个 README 作为第一个 commit，因为 Orbi 需要有 commit 才能从它拉分支。
</Note>

## 仓库要满足的条件

一个仓库只有满足下面几条才能被连接：

- 它**在你的 GitHub App 安装范围内**。Orbi 只看得见你授权过的仓库。
- 它**开启了 Issues**。Orbi 的输入渠道全部是 Issue，所以关掉了 Issues 的仓库在列表里会标上 **（Issue 功能已关闭，Orbi 无法正常工作）**，连接时也会被拒掉。先到仓库的 **Settings → Features → Issues** 里把它打开。
- 它**没有被归档**。归档的仓库会标上 **（已归档）**。

这些条件在你提交时都会重新检查，不只是在页面渲染时查一次，所以中间被取消授权的仓库也会被拦住。

## 列表里没有你的仓库时

列表里只有你的 App 安装覆盖到的仓库。如果你的不在里面，展开连接页上的 **没找到你的仓库？**：它会说明原因，并给出一个 **管理 App 授权** 链接，指向 GitHub 的 App 设置，你可以在那里把仓库加进安装范围。

你也可以选 **手动填写**，直接输入一个 `OWNER/REPO` 值。这在列表暂时读不出来的时候有用，但它不会绕过授权检查：App 访问不到的仓库在提交时照样会被拒掉。

<Frame caption="连接页的降级状态，有手动填写字段和一条说明原因的文字">
  <img src="/images/zh/connect-degraded.png" alt="连接页的降级状态，有手动填写字段和一条说明原因的文字" />
</Frame>

如果 GitHub 的仓库列表完全读不出来，页面会降级成手动填写并告诉你原因，不会把你堵在那里。

## 会卡住每一次合并的分支保护

如果你的基础分支要求合并前必须有批准评审，连接页会立刻提醒你，因为这个设置会让**每一次**交付都停在合并那一步。

原因在身份：Orbi 用同一个 GitHub App 的身份提交拉取请求并合并它，而 GitHub 不允许拉取请求的作者批准自己的拉取请求。在必须批准的规则生效时，每次交付都只能走到「评审过、可以合了」这一步，然后合不进去。状态页上这样的交付会显示 **等待审批**，标题会告诉你这个 PR 需要你 approve。

有三种解法，按你的策略挑一个：

1. **每次交付你自己批准**。你或者同事在拉取请求上点 **Approve**，合并就继续。每一个改动都有人把关。
2. **让 admin 可以绕过**。在 **Settings → Branches → Branch protection rules**（或者 **Settings → Rules → Rulesets**）下面开启 **Allow admins to bypass**，或者把这个账号加进 ruleset 的 bypass 列表。
3. **把必须批准数设成 0**，在同一处设置里改。

改完不需要重新连接，下一次交付的拉取请求就能正常合并。

## 连接多个仓库

如果你的套餐允许多个仓库，在状态页上点 **管理仓库**。连接页会显示你已用了多少、上限是多少（例如 **已用 1 / 上限 5 个仓库**），并列出已连接的仓库。选另一个仓库，点 **添加仓库**。每个仓库有自己的环境，各自开通。

连了不止一个仓库时，状态页会显示一个总览，每个仓库一行。点开一行就是这个仓库的详情：基础分支、交付范围、现在在发生什么、交付记录、版本，以及 **停用此仓库**。

## 更换绑定的仓库

所有套餐都是同一条规则：**先停用要换掉的仓库，再连接新的。** 连接新仓库不会自动替换旧的。

1. 点 **管理仓库**，在 **已连接仓库** 里找到要换掉的那个，点 **停用**，再点 **确认停用**。（在状态页的仓库详情里点 **停用此仓库** 也一样。）
2. 选新仓库，点 **添加仓库**。

停用会回收这个仓库的环境，但记录不会删：它会出现在状态页 **设置与参考** 的 **历史仓库** 里，交付和用量记录都在。以后再连接它，会重新开通，和任何新仓库一样需要一两分钟。

如果已经到了套餐上限还去连接新仓库，页面会显示 **已达到仓库数量上限**，并给出 **返回绑定页停用仓库**。Free 和 Solo 一次只能连一个仓库，页面上还会多一个 **升级到 Pro（最多 5 个仓库）**。

## 各种报错是什么意思

| 页面上写的 | 发生了什么 | 怎么办 |
|---|---|---|
| 仓库未被该 GitHub App 授权 | 仓库在你的安装范围之外 | 打开 GitHub App 的安装设置，把仓库加进去，刷新连接页 |
| **无法连接仓库**：GitHub Issues 已关闭 | 仓库关掉了 Issues 功能 | 在仓库的 **Settings → Features → Issues** 里打开，然后重试 |
| **已达到仓库数量上限** | 连接的仓库数已经到了套餐上限 | 先停用一个；Free 和 Solo 也可以升级到 Pro |
| 暂时无法读取仓库列表 | GitHub 的 API 连不上 | 重试；一直不行就用 **手动填写** |
| 仓库格式无效 | 手动填的值不是 `OWNER/REPO` | 按 `owner/repository` 重填，例如 `orbi-build/orbi` |

## 接下来会发生什么

连接会触发[开通](/zh/provisioning)：Orbi 搭起你的交付所运行的隔离环境，并把 `ai-*` 标签装进你的仓库。等 **开通环境** 这一步完成，就可以[把第一张 Issue 交给 Orbi](/zh/first-issue)。
