你在状态页上把一次发版规划成一个版本，等它的工作做完再开始发版；之后 Orbi 按确定的流程把它发出去。

你在状态页或 GitHub 决定版本并发起发布任务。之后 Orbi 核验范围和检查，按需更新指定版本文件，发布 tag 与 GitHub Release，再关闭 milestone。引擎的里程碑推进流程也可以在版本决策确认后创建发布任务，不会替你决定版本号。

发版不是一次开发交付。没有模型会话，也没有 pull request，它跑的是一个固定的状态机。

## 状态页上的版本

所有套餐都能使用版本。单项目时在状态页展开「用量与设置」→「版本」；多个项目时先进入该项目详情。版本管理和发版入口可见，不会增加免费交付次数或解除套餐额度。发版仍由你发起。

免费次数用完后，仍可新建版本和 Release 任务，但新的 Release 任务不能开始。订阅后在该 Issue 上重新加 `ai-ready` 才会派发。发版本身没有 PR，不计入前 3 次成功合并的交付；开始时仍需要可用名额。

一个版本就是一个标题为版本号的 GitHub milestone，比如 `v1.2.3`。这一块显示：

- 「当前版本：」Orbi 正在朝哪个版本做，或者「未设置（做所有已交给 Orbi 的任务）」。「在 GitHub 查看」打开这个 milestone；没设置时打开你仓库的 milestone 列表。
- 「未发布的版本」：你开着的版本 milestone，以及各自「未关闭的 Issue」的数量。其他版本提供「切换到这个版本」。当前那个版本标着「当前版本」，提供「创建 Release 任务」，建好之后换成「查看 Release 任务」。一个开着的 milestone 都没有时显示「暂无开放版本」。
- 「新建版本」：填一个版本号，点「新建并切换」。
- 「说明」：折叠起来的一段按钮说明。

### 当前版本

开放的「当前版本」限定新认领的 `ai-ready` Issue，只做这个 milestone 里的票；其他票等待，页面可提供「移到版本」或「切换到版本」。当前 milestone 已关闭且没有更新的开放 milestone 时，新认领不按里程碑过滤，配置值仍保留。有更新的开放 milestone 时，自动推进还是开版本确认票，由仓库的 `auto_next_milestone` 决定。已有交付的接续不受新票认领范围限制。

没有设置当前版本时，所有 `ai-ready` Issue 都可以被认领。用 Orbi 完全可以不用版本，只有当你想分批发布时它才有意义。

| 按钮 | 做什么 |
|---|---|
| 「新建并切换」 | 在 GitHub 上为你填的版本新建 milestone，并设为当前版本。不创建 Release 任务 |
| 「切换到这个版本」 | 把这个版本设为当前版本 |
| 「创建 Release 任务」 | 在你的仓库里开一张 Release vX Issue，打上 `ai-ready` 和 `ai-release`，并把这个版本设为当前版本 |

版本号必须是开头一个 `v`、后面跟点号分隔的数字，比如 `v1.2.3`；其他形状会在 GitHub 上发生任何改动之前就被拒绝。

## 发一个版本

一个版本的工作都进去了之后，如果它还不是当前版本，先点「切换到这个版本」，再在它那一行点「创建 Release 任务」。

Orbi 会开出 Release Issue。同一个 milestone 还有其他开放 Issue 时，发布票保持 `ai-ready` 排队，不会开始累计 30 分钟发布超时。范围就绪后，Orbi 执行发布，按需更新版本文件，打 tag，发布 GitHub Release 并关闭发布票。版本文件更新后，网站何时变化仍由你的发布或部署方式决定。

### milestone 是必需的

发版的 scope 来自标题与版本号完全一致的那个 milestone，所以 `v1.2.3` 需要一个叫 `v1.2.3` 的 milestone。「新建并切换」和「创建 Release 任务」在 milestone 不存在时都会替你建好；如果你手写 Release Issue，要自己确认 milestone 存在。

如果发版因为缺 milestone 停下，状态页上那张受阻的 Issue 会提供「创建版本并继续」。

### 创建 Release 任务或切换版本报错时

| 提示 | 原因 | 怎么修 |
|---|---|---|
| 「版本号格式不对：用 v 开头的数字，例如 v1.2.3。」 | 版本号不是 `vN.N…` 的形状 | 重填，例如 `v1.2.3` |
| 「没能创建 Release 任务：还没有连接仓库。」 | 这个账户还没有连接仓库 | [连接一个](/zh/connect-repository) |
| 「没能创建 Release 任务：暂时读不到项目根目录的版本文件，请稍后重试。」 | Orbi 找版本号文件时 GitHub 没有响应 | 稍后重试 |
| 「没能创建 Release 任务：GitHub 暂时没有响应，请稍后重试。」 | GitHub 不可达 | 稍后重试 |
| 「没能切换版本：这个项目没有连接到你的账户，什么都没改。」 | 切换版本时：仓库已断开，或者属于另一个账户 | [连接它](/zh/connect-repository) |
| 「没能切换版本：写入项目失败，什么都没改。在 GitHub App 设置里检查 Contents 写权限。」 | 切换版本时：Orbi 写不进这个仓库 | 检查 App 的权限，必要时重装 |

### 版本文件

Orbi 会探测你的项目用什么声明版本号，按这个顺序找：

`pyproject.toml`、`package.json`、`pom.xml`、`build.gradle`、`build.gradle.kts`、`gradle.properties`、`Cargo.toml`、`composer.json`、`pubspec.yaml`

一个都没有时是**只打 tag**：不修改版本文件，只生成 tag 和 GitHub Release。读不出仓库目录是需要重试的错误；成功读取后确实没有支持的版本文件，则是正常的 tag-only 结果。

## 自己手写 Release Issue

按钮只是个便利入口。你也可以手动建这张 Release Issue：打上 `ai-ready` 和 `ai-release`，并写一段 `## Release`：

```text
## Release

- version: v1.2.3
- base_branch: main
- version_file: package.json
- scope_from_milestone: v1.2.3
```

这一段是严格解析的：字段缺失、重复或出现未知字段都会立即失败。除了 `scope_from_milestone`，你也可以用 `#N` 的形式把 scope 逐条列出来。

## 打 tag 之前 Orbi 检查什么

门禁按顺序执行，查不了的门禁算没过。

**先冻结起始 base**：发布从基础分支的一个确定提交开始。需要改版本号时，会生成要发布的版本提交；检查和 tag 必须对应实际发布的那个提交。

**先检查 milestone，再认领发布票**：有其他开放 Issue 就继续排队。认领后出现同 milestone 的 `ai-in-progress`、`ai-pr-opened` 或 `ai-fix-needed` 交付时，执行中的门禁才等待这些任务，默认上限 30 分钟。单独的 `ai-ready` 不属于这层等待。仅有开放 PR 本身不构成发布门禁。

**发版 commit 上的 CI 必须是绿的。** 这就是测试验收，也是这里最值得搞明白的一条：

仓库上报的检查决定有哪些自动验收证据。从未观察到 CI 时，发布可以带着无检查证据通过，但这不证明测试通过。基础分支已有 CI 时，新推送的版本提交暂时没有检查，需要等检查注册；待完成或失败的检查不会当作通过。

pending 的 check 不算失败：门禁会等最终结论，默认最多等 30 分钟，等待期间持续上报进度。等待超时会如实报成超时，绝不会伪装成 CI 失败。

**scope 逐条实时核验。** 每一条要么是已合并的 PR，要么是以 completed 关闭的 Issue。Issue 正文里的勾选框完全不看，核验走 GitHub API。以 `not planned` 关闭的 Issue 会被记为排除，不进 changelog。

## 产出什么

- 在发版 commit 上创建一个**带注释的 tag**，用普通 push 推上去，永远不用 `--force`。已有 tag 不会移动；真正的 tag 冲突会让发布停下。恢复发布时，可以沿用已经位于基础分支历史中的既有 tag 提交。
- 发布一个 **GitHub Release**，release notes 里带完整证据：版本号、tag、发版 commit、逐条 scope 证据、门禁证据和测试证据。
- **关闭 milestone**。

每一步都是幂等的，所以在门禁上失败的发版，修掉原因后可以重试，它会接着跑而不是从头来。

## 发版失败时

CI 红了或超时会走正常的失败路径，Issue 被标记 `ai-blocked` 并写明原因。

这时版本号的 bump 可能已经落在你的基础分支上了，这是可接受的状态：bump 是幂等的，修好 CI 重跑一次会安全地把同一个版本再准备一遍。

## 为什么发版保持手动

版本和发布策略由你决定。可以在页面手动发起，或建带 `ai-ready` 与 `ai-release` 的 Issue；也可以在确认版本后，按已启用的里程碑流程创建发布任务。发布状态机负责检查和发布，不会独立决定产品范围。

<Note>
发版状态机属于引擎，不属于 Cloud。它的完整参考，包括每一道门禁、接续行为和写下的证据，在 [docs.orbi.build/zh/workflow](https://docs.orbi.build/zh/workflow)。
</Note>
