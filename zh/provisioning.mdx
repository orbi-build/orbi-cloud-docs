开通是搭起你的交付所运行的隔离环境，你一连接仓库它就自动开始。

它不用你触发，你也没法让它更快。正常需要**一到两分钟**，跑的过程中状态页会自己更新。

## 开通期间发生了什么

Orbi 创建一个专属于你这个仓库的环境，把仓库克隆进去，装上交付引擎，然后针对你的仓库跑一遍引擎的 setup 步骤。这个 setup 就是在你仓库的标签列表里创建 `ai-*` 标签的那一步 —— `ai-ready`、`ai-in-progress`、`ai-pr-opened`、`ai-fix-needed`、`ai-merged`、`ai-blocked` 以及其余几个。

setup 是声明式的：缺的标签会被创建，漂移了的会被纠回来，任何东西都不会被删。你自己的标签（`bug`、`enhancement`，不管你用什么）一概不碰。

每个环境严格对应一个租户和一个仓库。环境之间在操作系统层面相互隔离。

## 怎么看进度

**绑定的仓库** (Connected repository) 卡片里的**开通状态** (Provisioning status) 那一列显示它走到哪了：

| 你看到的 | 意思 |
|---|---|
| **正在开通** (Provisioning) | 在跑。通常一到两分钟；页面会自己刷新 |
| **开通成功** (Provisioned) | 完成。你可以[建第一张 Issue](/zh/first-issue) 了 |
| **开通失败** (Provisioning failed) | 停了。卡片会写明原因和下一步 |
| **—** | 开通从来没被触发过 —— 通常是因为还没连接任何仓库 |

## 开通失败时

失败从来不是死路，卡片总会同时给出一个原因和一个下一步。一共分四类：

### GitHub App 的安装或授权已失效

Orbi 没法再为你的安装签出 token 了 —— 通常是因为 App 被卸载了，或者它对这个仓库的访问权限被去掉了。

**怎么办**：重新安装或重新授权 GitHub App，然后重试。卡片上有指向连接页的链接。

### 模型凭据没有被接受

你自己的模型 key 被 provider 拒了。

**怎么办**：打开[模型配置](/zh/model-configuration)，把 key 改对。保存新配置会自动重试开通 —— 你不需要重新连接仓库。

### 模型服务连不上

key 或者 base URL 看起来是错的，或者 provider 不可达。

**怎么办**：在[模型配置](/zh/model-configuration)页上检查 base URL 和 key。同上，保存会自动重试开通。

### 平台一侧的故障

凡是不能归因到你的安装或你的模型配置的，都是我们这边的问题。

**怎么办**：什么都不用做。平台会自动恢复。卡片会明确这么写，并请你一两分钟后再回来看。如果过了这个时间还没恢复，联系技术支持 —— 卡片里带一个 **request id**，能定位到你这一次具体的开通尝试，把它一起报上来。

## 重试

开通会自动重试有限的次数。卡片会告诉你你处在哪种情况：要么**开通会自动重试**，要么**自动重试次数已用完**。

如果是租户一侧的原因导致重试用尽，把原因修掉就会重新武装它 —— 保存一份改对了的模型配置，即使已经用尽次数也会重试。如果是平台一侧的原因导致用尽，平台恢复会接手，不需要你做任何事。

## 开通成功之后

不需要再做别的。环境会保持开通状态；两次交付之间你不用重新开通。[建一张 Issue 并打上 `ai-ready`](/zh/first-issue)。

连接一个**不同的**仓库，会为它重新开通一个新环境。
