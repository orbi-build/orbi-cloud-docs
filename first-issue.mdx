Dispatching work to Orbi requires nothing more than a normal GitHub Issue and a single label. Add `ai-ready` to any Issue in your connected repository and Orbi picks it up automatically — no command, no form, no separate queue. Pickup happens on a timer, so allow up to 5 minutes for `ai-in-progress` to appear.

## Dispatch an Issue

<Steps>
  <Step title="Create a GitHub Issue">
    In your connected repository, open a new Issue and describe the one change you want made. Be as specific as you can about what should change and how you will know it worked.
  </Step>
  <Step title="Add the ai-ready label">
    Apply the `ai-ready` label to the Issue. This label was created automatically when you provisioned your repository — you do not need to create it yourself.
  </Step>
  <Step title="Watch for pickup">
    Within approximately 5 minutes the `ai-ready` label is replaced by `ai-in-progress`, and the Issue appears under the **Doing** tab on the status page. You will also see activity in any CI checks tied to the working branch.
  </Step>
</Steps>

<Note>
  Orbi only processes Issues in the single repository you have connected. Issues in other repositories — even ones you own — are ignored until you connect them.
</Note>

The status page at [orbi.build/api/](https://orbi.build/api/) provides two shortcuts if you prefer to start from there. The **"Let Orbi try this one"** button applies the `ai-ready` label to an existing Issue for you. The **"Create an Issue"** button opens GitHub's new-Issue form with the label pre-selected so it is dispatched the moment you save.

## How to Write a Good Issue

<Frame caption="The status page listing untagged Issues with Let Orbi try this one buttons">
  <img src="/images/status-ready-issues.png" alt="The status page listing untagged Issues with Let Orbi try this one buttons" />
</Frame>

- **Say what should change and where.** "The export button on the Orders page produces a CSV with no header row; it should include one" gives Orbi a precise target. "Fix export" does not.
- **Say how you'll know it worked.** The acceptance criterion you write is exactly what the independent review checks. "A downloaded CSV starts with a header row" is checkable. "Export works properly" is not.
- **One Issue, one change.** Bundling several changes into a single Issue produces a bundled PR that is harder to review and more likely to fail the independent review stage.
- **Name constraints explicitly.** If a public API must not change, say so in the Issue body. Orbi will not infer prohibitions — anything not stated as off-limits is fair game.
- **Don't ask for production evidence.** The delivery environment contains your repository and its tests, not your production credentials or live site. Issues that require production data, live service calls, or environment secrets will be marked `ai-blocked`.

## Priority

By default, Orbi picks up Issues in the order they become `ai-ready`. To move an Issue ahead of the queue, add the `p0` label alongside `ai-ready`. Pickup order is: `p0`-labelled Issues first, then Issues labelled `bug`, then everything else.

## Task Types

The `ai-ready` label on its own dispatches a standard development task — coding, PR, independent review, and merge. Pair it with a second label to request a different type of work.

| Task Type | Labels | What You Get |
|---|---|---|
| Development (default) | `ai-ready` | Full chain: coding, PR, independent review, merge |
| Release | `ai-ready` + `ai-release` | Deterministic release state machine |
| Ops / Research | `ai-ready` + `ai-ops-only` | Full execution session; deliverable is evidence posted on the Issue |
| Content | `ai-ready` + `ai-content-only` | Text in, text out, delivered as an Issue comment — no git |

## Steering a Delivery in Flight

If a delivery is running and you realise the scope needs to change, you do not have to wait for it to finish. While the `ai-in-progress` label is present, add a comment to the Issue or edit the Issue body with your correction. Orbi restarts the session with your updated instructions within approximately 1 minute.

Two limits apply: each delivery supports a maximum of 3 steering restarts, and only repository owners, maintainers, members, and collaborators can trigger a restart. This prevents public commenters from redirecting a running session.

<Tip>
  For a full explanation of how steering fits into the delivery flow, see [Steering a Running Delivery](/delivery-lifecycle#steering-a-running-delivery).
</Tip>

## Choosing Your First Issue

For your first dispatch, pick something small and well-scoped: a bug with a clear reproduction step, a missing test, or a contained refactor with a defined boundary. A tight scope makes it easy to verify the result and gives you a clean end-to-end view of how Orbi works. Save ambiguous architectural decisions or open-ended exploratory work for after you have seen a successful delivery.
