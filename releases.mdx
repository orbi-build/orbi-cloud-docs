Releases in Orbi are never automatic. You name the version, you decide when to cut it, and Orbi runs the same deterministic process every time — the same gates, in the same order, producing the same evidence. Nothing is published until every gate passes.

## Cut a Release

<Steps>
  <Step title="Open the status page">
    Go to [orbi.build/api/](https://orbi.build/api/) and find the **Connected Repository** card.
  </Step>
  <Step title="Enter the version">
    In the **Cut a release** form, type the version in the format `v1.2.3` — a leading `v` followed by dot-separated integers. No pre-release suffixes, no build metadata.
  </Step>
  <Step title="Submit the form">
    Click **Cut a release**. Orbi creates a Release Issue labelled `ai-ready` + `ai-release` and takes you to it on GitHub. From that point, progress follows the standard `ai-*` label sequence.
  </Step>
</Steps>

### The Milestone Requirement

The scope of a release comes from a GitHub milestone whose title matches the version exactly — for example, a milestone named `v1.2.3` for a release of `v1.2.3`. Orbi does **not** create the milestone for you. Before you cut a release, create the milestone in your repository and assign every Issue and PR that belongs in this release to it. Orbi reads the milestone live at claim time.

## Form Errors

| Message | Cause | Fix |
|---|---|---|
| Invalid version | Not in `vN.N.N` format | Retype the version, e.g. `v1.2.3` |
| No repository | No active repository is connected | Connect a repository first |
| Version file could not be probed | Orbi could not detect a version declaration in your repository | See version file detection below |
| GitHub error | GitHub was unreachable or the App lacks the necessary permission | Retry; reinstall the GitHub App if the error persists |

## Version File Detection

Orbi inspects your repository for a recognisable version declaration. It checks these files in order and uses the first one it finds:

1. `pyproject.toml`
2. `package.json`
3. `pom.xml`
4. `build.gradle`
5. `build.gradle.kts`
6. `gradle.properties`
7. `Cargo.toml`
8. `composer.json`
9. `pubspec.yaml`

If none of these files is present, Orbi performs a tag-only release and skips the version bump entirely. Orbi will not guess at an undeclared version location.

## Writing the Release Issue Manually

The form is a convenience. If you prefer, create the Release Issue yourself: open a new Issue in your connected repository, apply the `ai-ready` and `ai-release` labels, and include a `## Release` section in the body.

```text
## Release

- version: v1.2.3
- base_branch: main
- version_file: package.json
- scope_from_milestone: v1.2.3
```

Orbi parses this section strictly. Missing fields, duplicate fields, or unrecognised field names all cause an immediate failure. The `version_file` field must name a file that exists in the repository; the `scope_from_milestone` field must match an existing milestone title exactly.

## What Orbi Checks Before Tagging

Orbi runs four gates in order. All four must pass before the tag is created.

1. **Base is frozen.** The release commit must equal the tip of the base branch at the moment Orbi claimed the Issue. If someone pushes to the base branch while the release is running, this gate fails.
2. **No unfinished scope.** No Issue in the milestone may carry an `ai-in-progress`, `ai-pr-opened`, or `ai-fix-needed` label. Finish all in-flight work before cutting the release.
3. **CI is green.** Orbi waits for all check runs on the release commit to complete, up to 30 minutes. A single failing check blocks the release.
4. **Every scope item verified.** Each Issue and PR in the milestone is checked live via the GitHub API. An Issue must be closed as completed; a PR must be merged.

<Note>
  Your CI configuration defines what Orbi guarantees. If your repository has no CI, all check-run gates pass automatically and Orbi records explicit "no check runs" evidence in the GitHub Release.
</Note>

## What a Release Produces

A successful release creates three artefacts:

- **An annotated git tag** at the release commit. The tag is never force-pushed. If the tag already exists at a different commit, the release fails rather than overwrite it.
- **A GitHub Release** with full evidence: version, tag, commit SHA, per-item scope evidence (merged PR or closed Issue), gate evidence, and test evidence.
- **A closed milestone.** Orbi closes the milestone after the GitHub Release is published.

## Why Releases Stay Manual

The `ai-release` label is the one label Orbi never applies to an Issue on its own. Every other label transition is automatic — but publishing a tag is not. A tag is difficult to retract cleanly once other systems have seen it, and the decision to publish belongs to you, not to an automated process. The form exists to make that decision quick; the requirement to make it remains yours.
