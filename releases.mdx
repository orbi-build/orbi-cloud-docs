You plan a release as a version on the status page, and when its work is done you start the release; Orbi runs it deterministically from there.

You choose the version and initiate a release task, from the status page or GitHub. Orbi then verifies its scope and checks, updates the declared version file when needed, publishes the tag and GitHub Release, and closes the milestone. Enabling the engine’s milestone-advance workflow can also create a release task after a confirmed version decision; it does not choose a version on your behalf.

A release is not a development task. There is no model session and no pull request; it runs a fixed state machine.

## Versions on the status page

Versions are available on every plan. For one project, open **Usage and settings** → **Versions**; with several projects, open the project’s detail view first. Version management and the release entry point do not add free deliveries or remove plan limits. You still decide when to release.

After the free allowance is used up, you can still create versions and release tasks, but a new release task cannot start. Subscribe, then reapply `ai-ready` to that Issue to dispatch it. A release has no PR and does not count as one of the first 3 merged deliveries; it still needs an available slot to start.

A version is a GitHub milestone whose title is the version number, like `v1.2.3`. The section shows:

- **Current version:** the version Orbi is working towards, or **Not set (works on every task handed to Orbi)**. **View on GitHub** opens the milestone, or your repository's milestones when none is set.
- **Unreleased versions**: your open version milestones, with their **Open Issues** count. Other versions offer **Switch to this version**. The current one is marked **Current version** and offers **Create release task**, or **View release task** once it exists. With no open milestones this reads **No open versions**.
- **New version**: type a version and click **Create and switch**.
- **Guide**: a short folded explanation of the buttons.

### The delivery scope

An open **Current version** limits fresh `ai-ready` pickup to that milestone; Issues outside it wait. The status page can offer **Move to version** or **Switch to version**. If the current milestone is closed and there is no newer open milestone, pickup runs without a milestone filter while keeping the configured value. If a newer open milestone exists, automatic advancement or a version-confirmation Issue depends on the repository’s `auto_next_milestone` policy. Existing deliveries resume independently of the fresh-pickup scope.

While no version is set, every `ai-ready` Issue is eligible. You do not need versions at all to use Orbi; they only matter once you want to ship in batches.

| Button | What it does |
|---|---|
| **Create and switch** | Creates the milestone for the version you typed on GitHub and makes it the current version. It does not create a release task |
| **Switch to this version** | Makes that version the current version |
| **Create release task** | Opens a **Release vX** Issue in your repository, labelled `ai-ready` and `ai-release`, and makes that version the current version |

Version numbers must be a leading `v` followed by dot-separated numbers, such as `v1.2.3`; anything else is rejected before anything is changed on GitHub.

## Cut a release

When the work for a version is in, make it the current version with **Switch to this version** if it is not already, then click **Create release task** on its row.

Orbi opens the Release Issue. While any other Issue in that milestone is still open, it leaves the release queued at `ai-ready`; this wait does not consume a 30-minute release timeout. After the milestone is ready, Orbi runs the release, updates the version file when applicable, tags and publishes the GitHub Release, and closes the Issue. Updating the version file affects your site only through your own release or deployment process.

### The milestone requirement

The release scope comes from the milestone whose title is exactly the version, so `v1.2.3` needs a milestone called `v1.2.3`. **Create and switch** and **Create release task** both create that milestone for you if it does not exist; if you write a release Issue by hand, make sure the milestone exists.

If a release stops because the milestone is missing, the blocked Issue on the status page offers **Create the milestone and continue**.

### If creating a release task or switching versions reports an error

| What it says | Cause | Fix |
|---|---|---|
| **That version number is not valid: use a number starting with v, for example v1.2.3.** | The version is not `vN.N…` | Retype it, for example `v1.2.3` |
| **No connected repository: connect one first, then cut a release.** | No repository is connected to this account | [Connect one](/connect-repository) |
| **The repository root could not be read right now (GitHub API error), so no Release Issue was created; please retry later.** | GitHub did not answer when Orbi looked for the version file | Retry later |
| **GitHub did not respond, so the Release Issue was not created; please retry later.** | GitHub could not be reached | Retry later |
| **This repository is not connected to the current account. The delivery scope was not changed.** | When switching versions: the repository was disconnected or belongs to another account | [Connect it](/connect-repository) |
| **The repository delivery scope was not changed, and the control plane was not changed either. Check the GitHub App's Contents write permission and try again.** | When switching versions: Orbi could not write to the repository | Check the App's permissions; reinstall it if needed |

### The version file

Orbi detects how your project declares its version, checking in this order:

`pyproject.toml`, `package.json`, `pom.xml`, `build.gradle`, `build.gradle.kts`, `gradle.properties`, `Cargo.toml`, `composer.json`, `pubspec.yaml`

If none is present, the release is **tag-only**: no version-file update, just the tag and GitHub Release. A failure to read the repository tree is an error to retry; a successful read finding no supported file is a valid tag-only result.

## Writing the Release Issue yourself

The buttons are a convenience. You can create the Release Issue by hand instead — label it `ai-ready` and `ai-release`, and give it a `## Release` section:

```text
## Release

- version: v1.2.3
- base_branch: main
- version_file: package.json
- scope_from_milestone: v1.2.3
```

The section is parsed strictly: a missing, duplicated or unknown field fails immediately. Instead of `scope_from_milestone` you may list the scope explicitly as `#N` references.

## What Orbi checks before it tags

The gates run in order, and a gate that cannot be checked counts as failed.

**The starting base is frozen first.** The release starts from a specific base-branch commit. When a version bump is needed, that produces the version commit to be released; the checks and tag must refer to the actual release commit.

**Milestone admission comes before execution.** Another open Issue in the milestone keeps the release unclaimed. If a delivery appears after admission, the in-run gate waits for same-milestone `ai-in-progress`, `ai-pr-opened` or `ai-fix-needed` work, with its own default 30-minute bound. A bare `ai-ready` label is not an in-run delivery wait. Open PRs alone are not a release gate.

**CI must be green on the release commit.** This is the test acceptance, and it is the part worth understanding properly:

Your repository’s checks determine the automated evidence available. With no observed CI, the release can proceed with explicit no-checks evidence; that does not prove tests passed. Once CI has been observed on the base, a newly pushed version commit with no checks yet must wait for them to register. Checks that are pending or failed cannot be treated as passed.

A pending check is not a failure: the gate waits for the final conclusion, up to 30 minutes by default, reporting progress while it waits. A timeout is reported as a timeout, never disguised as a CI failure.

**Every scope item is verified live.** Each item must be a merged pull request, or an Issue closed as completed. Checkbox state in the Issue body is ignored entirely — the check goes to the GitHub API. An Issue closed as "not planned" is recorded as excluded and left out of the changelog.

## What it produces

- An **annotated tag** at the release commit, pushed normally — never with `--force`. An existing tag is never moved; a conflicting tag stops the release. A resumed release can use its existing tag commit when that commit is already in the base branch’s history.
- A **GitHub Release** whose notes carry the full evidence: version, tag, release commit, per-item scope evidence, gate evidence and test evidence.
- The **milestone closed**.

Every step is idempotent, so a release that failed on a gate can be retried after you fix the cause — it resumes rather than starting over.

## When a release fails

A red or timed-out CI takes the normal failure path and the Issue is marked `ai-blocked` with the reason.

The version bump may already be on your base branch at that point, which is an acceptable state: the bump is idempotent, so repairing CI and re-running prepares the same version again safely.

## Why releases stay manual

You decide the version and release policy. Start a release manually with the page action or an `ai-ready` + `ai-release` Issue, or use the engine’s configured milestone workflow after confirming its version decision. The release state machine then performs the checks and publication; it does not independently decide product scope.

<Note>
The release state machine is the engine's, not Cloud's. Its full reference — every gate, the resume behaviour and the evidence it writes — is at [docs.orbi.build/workflow](https://docs.orbi.build/workflow).
</Note>
