Connecting a repository tells Orbi which repository's Issues it may work on, and which branch to open pull requests against.

Connecting is self-service: you pick the repository and the base branch on the connect page, and provisioning starts immediately. How many repositories can be connected at the same time depends on your plan — one on Free and Solo, up to five on Pro. See [limits and quotas](/limits-and-quotas).

## Connect

From the status page, click **Connect repository** (or **Add repository** once you already have one).

<Frame caption="The Connect repository page, showing the repository and base branch lists">
  <img src="/images/connect.png" alt="The Connect repository page, showing the repository and base branch lists" />
</Frame>

1. **Repository** — pick from the repositories your GitHub App installation covers. With a long list, type part of the name into the search box to filter it.
2. **Base branch** — the branch Orbi opens pull requests against. Selecting a repository loads its real branches and preselects its default branch, so usually you just confirm.
3. Click **Connect repository**. The button changes to **Connecting…** while it works; you do not need to click again.

The page then says **Repository connected** and starts [provisioning](/provisioning). It updates itself, and a **Create your first Issue** button appears when the environment is ready.

<Note>
If the repository is empty — no commits at all — the page tells you, and Orbi commits a README as the first commit on the base branch when you connect. Orbi needs a commit to branch from.
</Note>

## Requirements a repository has to meet

A repository can only be connected if:

- It is **covered by your GitHub App installation**. Orbi only sees repositories you authorized.
- It has **Issues enabled**. Orbi's entire input channel is Issues, so the list marks such a repository **(Issues are turned off — Orbi can't work here)**, and connecting it is rejected. Turn Issues on under the repository's **Settings → Features → Issues** first.
- It is **not archived**. Archived repositories are marked **(archived)**.

These are checked when you submit, not just when the page renders — so a repository that was de-authorized in between is caught.

## When your repository is not listed

The list only contains repositories your App installation covers. If yours is missing, open **Cannot find your repository?** on the connect page: it explains the cause and has a **Manage App authorization** link to GitHub's App settings, where you can add the repository to the installation.

You can also choose **Enter manually** to type an `OWNER/REPO` value directly. That is useful when the listing is temporarily unavailable, but it does not bypass the authorization check — a repository the App cannot access is still rejected on submit.

If GitHub's repository listing cannot be read at all, the page degrades to manual entry and tells you why, rather than blocking you.

## Branch protection that blocks every merge

If your base branch requires approving reviews before merge, the connect page warns you immediately, because this setting stops **every** delivery at the merge step.

The reason is identity: Orbi opens the pull request and merges it as the same GitHub App, and GitHub does not let a pull request's author approve their own pull request. With required approvals in force, each delivery gets as far as a reviewed, ready pull request and then cannot merge it. On the status page such a delivery shows **Awaiting approval**, and the headline says the pull request needs your approval.

Three ways to resolve it — pick whichever suits your policy:

1. **Approve each delivery yourself.** You or a colleague clicks **Approve** on the pull request, and the merge proceeds. Keeps a human in the loop on every change.
2. **Let admins bypass.** Under **Settings → Branches → Branch protection rules** (or **Settings → Rules → Rulesets**), enable **Allow admins to bypass**, or add the account to the ruleset's bypass list.
3. **Set required approvals to 0** in the same setting.

Changing it does not require reconnecting — the next delivery's pull request merges normally.

## More than one repository

On a plan that allows several repositories, click **Add repository** on the status page — or on the connect page, where it shows how many you have used against your limit (for example **Used 1 / limit 5 repositories**). Each repository gets its own environment and its own provisioning.

With more than one repository connected, the status page shows an overview with one row per repository. Click a row to open that repository's detail: its base branch, its delivery scope, what is happening now, its delivery history, its versions, and **Deactivate this repository**.

When you are at your limit, the connect page says **Repository limit reached**. Deactivate a repository you no longer need, or move to a plan with more — the page offers **Upgrade to Pro (up to 5 repositories)**.

## Changing the connected repository

On a plan with a single repository, connecting a different one replaces the current one: the new repository becomes active, and the previous one moves to history. It is not deleted — it still appears under **Historical repositories** in **Settings and reference** on the status page, with its delivery and usage history.

You can also take a repository out of service without replacing it: **Deactivate** on the connect page (or **Deactivate this repository** in the repository's detail), then **Confirm deactivation**. Deactivating reclaims that repository's environment; its delivery and usage history remains available. Connecting it again later provisions it afresh.

Every newly connected repository is provisioned from scratch, which again takes a minute or two.

<Note>
You cannot change repositories while a delivery is in flight. The page says **Repository connected; cannot change it yet** and asks you to wait until the current delivery ends — its pull request merged, or its Issue closed. This protects the running delivery.
</Note>

## What the errors mean

| What the page says | What happened | What to do |
|---|---|---|
| The repository is not authorized for the GitHub App | The repository is outside your installation's scope | Open the GitHub App installation settings, add the repository, reload the connect page |
| **Cannot connect repository** — GitHub Issues disabled | The repository has the Issues feature turned off | Enable it under the repository's **Settings → Features → Issues**, then retry |
| **Repository connected; cannot change it yet** | A delivery is running in the currently connected repository | Wait for it to finish, then change |
| **Repository limit reached** | You already have as many repositories as your plan allows | Deactivate one, or upgrade to Pro |
| The repository list was temporarily unavailable | GitHub's API could not be reached | Retry; use **Enter manually** if it persists |
| Invalid repository format | The manually entered value is not `OWNER/REPO` | Re-enter as `owner/repository`, for example `orbi-build/orbi` |

## What happens next

Connecting starts [provisioning](/provisioning) — Orbi builds the isolated environment your deliveries run in and installs the `ai-*` labels into your repository. When **Provision environment** is done, [hand Orbi its first Issue](/first-issue).
